# SCOUT API contracts and Phase 2 boundary

This repository currently has established, unversioned contracts for the venue host and the hosted account service. Phase 2 keeps them in place; it does **not** switch the desktop, website, or venue host to a new protocol.

## Compatibility policy

- The venue host API and WebSocket contracts remain as inventoried in [`API-AUDIT.md`](API-AUDIT.md).
- The account service contract remains the legacy v1-compatible API documented in [`BETA.md`](BETA.md) and implemented by `server/account-service.ts`.
- The host's `/api/beta/*` proxy continues forwarding the established request and response bodies to the account service.
- No public account-registration, lease, release-signing, telemetry, or updater endpoints are introduced in Phase 2.
- Existing success response bodies and the legacy error fields (`error`, `code`) are unchanged. Account-service error responses now add a `requestId` field; every response also carries the same ID in `X-Request-Id`. Clients that only read the previous fields remain compatible.
- Request IDs are generated by the service (incoming IDs are not trusted), scoped to one request, and safe to include in support requests. They are not authentication credentials. The account service returns `requestId` in errors and the host exposes `X-Request-Id` on every response, adding `requestId` to existing error objects that already have an `error` field.

## Current account-service routes

The upstream paths below are served by the hosted account service. Venue-host/browser paths are prefixed with `/api/beta/` except host-local link routes; see `BETA.md` for the proxy boundary.

| Method | Path | Access boundary | Request | Success |
| --- | --- | --- | --- | --- |
| GET | `/healthz` | public, operational status only | — | `{ok, accounts, pending, devices}` |
| GET | `/status` | public or own `scout_account` cookie | — | `BetaStatusView`; only an approved account gets download details |
| POST | `/apply` | public; rate-limited | `ApplicationInput` plus optional legacy `address` field | `{account, invite:null}`; creates no authenticated account |
| POST | `/login` | public; failure-throttled | `{email, password}` | `{account}` and HttpOnly session cookie |
| POST | `/logout` | public; revokes the presented session | cookie | `{ok:true}` and cleared cookie |
| POST | `/activate` | public; single-use invitation | `{invite, password}` | `{account}` and HttpOnly session cookie |
| GET | `/applications` | constant-time configured service-key comparison | — | `{applications: AccountView[]}` |
| POST | `/applications/{id}` | service key | `{decision:'approve'\|'reject', decidedBy?}` | `{account, invite}`; invite is shown once to the operator |
| GET | `/settings` | service key | — | `{settings}` |
| PUT | `/settings` | same-origin approved owner session; owner email configured server-side | partial settings | `{settings}` |
| POST | `/device/start` | public; pending-grant cap | `{label, platform, origin}` | `DeviceGrantView` |
| POST | `/device/poll` | one-time device-code credential | `{deviceCode}` | `DevicePollView`; installation token is returned once |
| POST | `/device/approve` or `/device/deny` | approved account session | `{userCode}` | `{account}` |
| POST | `/devices/revoke` | account session, own device only | `{deviceId}` | `{account}` |
| POST | `/license/check` | installation token; internal account resolution additionally requires service key | `{deviceId, installationId, token, resolveAccount?}` | `{status:'active'\|'revoked'\|'unknown', ...}` |

The contract's existing field types are exported from `server/beta.ts`. Error responses retain their historical fields and add request correlation:

```json
{"error":"That request is not authorized.","code":"no-session","requestId":"<service-generated UUID>"}
```

`X-Request-Id` is returned on both successful and failed account-service responses. Unexpected failures return a generic message; server logs contain only the request ID and error class, not the exception text or request body.

## Authorization boundaries

`server/account-service.ts` centralizes checks in its `requireServiceKey`, `requireAccount`, `requireOwnerAccount`, and `requireSameOrigin` guards. Service-key authority is restricted to machine-facing operations. It cannot substitute for the owner's authenticated session on settings changes. Account-owned installation operations scope database lookups by the authenticated account ID. There is still no public registration route.

## Database migration contract

`server/account-migrations.ts` uses SQLite `PRAGMA user_version` and forward-only, transactional migrations. Version 1 adopts the pre-existing account-service tables through `CREATE TABLE IF NOT EXISTS`; it does not rebuild them. Version 2 adds:

- a backfilled `normalized_email` value matching `trim().toLowerCase()` plus a unique index;
- indexes for session expiry, grant expiry/status, active devices and audit queries;
- a dedicated `audit_logs` table with actor/action/target/request correlation and JSON metadata.

The older `events` table and its readers remain untouched. Audit metadata deliberately excludes the legacy free-form event detail, which can contain personal data or one-time codes. The migration will refuse to start if pre-existing account emails collide after trimming and case normalization; the error instructs operators to back up and resolve those rows, and SQLite rolls back the migration.

## Deliberately not in this phase

Phase 2 does not add account invitations by email, password recovery, public `/api/v1` routes, accounts/roles/entitlements as new relational entities, desktop authentication migration, signed leases, tournament accounting, update metadata, or telemetry collection. They remain gated for their scheduled phases, and no client is made dependent on those endpoints.
